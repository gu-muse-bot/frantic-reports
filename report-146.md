I first ran nitro_send_test_message to my own inbox (spam score 0, provider accepted) and the read-only nitro_review_delivery preflight, and only then called nitro_send_message once, to proof@dogfood.nitrosend.net, from hello@emberline-coffee.nitrosend.net — message ID 5488389, status "sent" with an Amazon SES provider ID.
- **Time.** About 66 minutes from opening the v0 gallery to the accepted verification send (17:04 → 18:09 Bangkok), including two human-assisted sign-in steps.
- **Slowest step.** The sign-in chain, by far: v0 sign-up routed through Vercel account creation with an SMS code plus an email confirmation code, then a separate Google sign-in for Nitrosend. The human-in-the-loop logins took longer than the design work and both sends combined.
- **Friction worth knowing.** (1) nitro_send_message rejects a template send without an explicit subject even though the template already carries one — undocumented, found only from the validation error; the failed call dispatched nothing and I retried with the subject repeated. (2) The MCP preflight (nitro_review_delivery) blocked on a missing physical address in the Brand Kit, although the web editor's setup flow never asked for one; I fixed it via nitro_set_brand_kit and the re-run came back ready with zero blockers. (3) Test sends also require an idempotency_key, which the tool schema does not mark as required. (4) The gallery template ships an empty leftover footer link that the editor would not let me delete, so two accessibility warnings persist (1 link missing accessible text, 2 low-contrast pairs — one inherited grey-on-black footer text, one my own specified white-on-ember CTA).
- **One change I would make.** Surface the physical-address requirement where the work happens: prompt for it during onboarding or inside the editor's send flow, not only in the MCP preflight — a web-only user would hit the same wall later and with less context. Runner-up: let nitro_send_message inherit the saved subject when a template_id is given, or document that it cannot.
